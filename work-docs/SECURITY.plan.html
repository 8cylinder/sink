01Executive summary

Sink's execution architecture is good. The command layer builds argv arrays, never uses shell=True, quotes rendered commands with shlex, validates paths, checks gzip magic, sanitizes dump names, streams pipelines, stages remote MySQL credentials as 0600 files over SSH stdin with an EXIT trap, defaults to dry-run, does not add --delete by default, and uses batch SSH probes with host-key checking.

What is already strong

  • No shell interpolation for ordinary commands. subprocess receives argv lists; shlex.join is used for rendered commands. There is no shell=True in src/.
  • Path and name validation. Transfer paths are resolved and checked against the project root; dump tags reject separators and ..; project/server names are reduced to one filename component; imports validate gzip magic before running remote commands.
  • Credentials handled out of band on the remote side. Remote MySQL passwords are written with umask 077; cat > path over SSH stdin, referenced by --defaults-extra-file, removed by an EXIT trap, with a separate cleanup command as fallback.
  • Safe defaults. Destructive commands are printed unless --real is passed; rsync receives its native --dry-run; no --delete or --remove-source-files is added by Sink; pipelines stream rather than buffering payloads.
  • Some output redaction exists. misc api masks sensitive key names, misc settings masks configured secrets, and pipeline errors can be passed a secrets tuple.
  • Batch probes are conservative. Check, actions, and credential staging use BatchMode=yes and StrictHostKeyChecking=yes through _ssh_base.
  • Failure signals are mostly honest. Pipeline execution reports the first non-zero stage; DB pull avoids updating LATEST-* on ordinary failure; dump collisions are avoided with unique names.

The main risk is trust-boundary and data handling, not shell injection

The serious issues are: what gets uploaded when the project root is the repository, what gets printed when secrets are in the config, what a symlink can reach, how local dumps are stored, and what sink.yaml is allowed to execute. A malicious repo or parent-directory config is equivalent to a shell script plus a credential store; Sink does not sandbox it. That trust assumption must be explicit before anyone runs sink check or --real in an unfamiliar checkout.

Trust assumption to state in the README and SECURITY.md

sink.yaml is executable code and trusted credential material. It can choose the SSH host, identity, MySQL host, URL targets, child process binary, remote shell fragment, diff tool, and action commands. Anyone who can write sink.yaml — or place one in a parent directory that Sink discovers — can cause code execution or credential exfiltration in the operator's context. Treat configs like shell scripts: review them, keep them in trusted repositories, restrict write access, and never run sink check or --real against an unreviewed checkout without reading the config and knowing which file was resolved.

05Remediation plan

Sequence matters: stop secret and data exposure first, then make failures and SSH trustworthy, then finish hardening. Phase 0 items are small, local, and independently shippable. Phase 1 changes command construction and failure semantics. Phase 2 is defense in depth and supply-chain work.

Phase 0 — Stop the bleeding

1–3 days · P0

  • SEC-01 safe excludes + narrow starter root
  • SEC-02 redact info, honor quiet
  • SEC-03 --safe-links, nested-symlink tests
  • SEC-04 0600 dumps, 0700 pulls, per-stage env
  • SEC-05 trust warning + resolved config path
  • SEC-08 clean partial dumps on interrupt
  • SEC-09 narrow temp cleanup

Exit: no test can upload a secret-looking file, print a configured password, escape via a nested symlink, or leave a readable dump.

Phase 1 — Make failure and SSH honest

1–2 weeks · P1

  • SEC-06 aggregate check failures, non-zero exit
  • SEC-07 strict SSH options everywhere
  • SEC-10 missing key is a hard error in real mode
  • SEC-11 MySQL TLS configuration
  • SEC-12 block dangerous rsync flags
  • SEC-13 pull confirmation / clean-tree guard
  • SEC-14 quote --rsh with shlex.join
  • SEC-16 central redaction across surfaces

Exit: CI cannot pass a broken check; rsync cannot silently trust an unknown key; a remote pull cannot overwrite a dirty tree without consent.

Phase 2 — Defense in depth

2–4 weeks · P2

  • SEC-15 private remote temp dir, control-char rejection
  • SEC-17 safe YAML generation for misc init
  • SEC-18 success ordering, Rich markup, git flags, pager/PATH, CI pinning, YAML cycles, skip_secure_auth

Exit: no known low-severity path remains; residual risks are documented, owned, and re-tested each release.

06Decisions required

Seven product decisions determine whether the fixes are compatible with existing workflows. Recommendations are written to fail closed while giving operators an explicit, auditable escape hatch.

D1Non-overridable safe excludes?

Recommendation: make secret-material excludes non-overridable and add a per-path --allow-secret-files that prints the exact paths and requires an interactive confirmation.

sink.yaml, *.sql.gz, .env*, *.pem, *.key, .ssh/, .git/, and cloud credential directories should never be transferred by a generic whole-project command. Explicit single-file transfers remain possible with the override. Document that safe excludes are evaluated before per-server includes.

D2Check fail default or --strict?

Recommendation: ship --strict immediately, make failure the default in the next minor, and keep --allow-failures as the explicit compatibility opt-out. Add --json for CI.

Changing the default is a breaking change for scripts that expect 0. Deprecate with a warning in 0.3.x, then flip in 0.4.0. The current test that asserts exit 0 must be updated, not preserved.

D3Config discovery boundary?

Recommendation: stop at the nearest repository root (directory containing .git) or after a bounded number of parents, and never cross into $HOME//tmp implicitly. Print the resolved path. Require --config PATH or --trust-parent-config to go further.

Keep monorepo support by allowing an explicit config path and an environment variable. Flag configs outside the repo or owned by a different user. This removes the “planted parent config” attack without removing intentional workflows.

D4MYSQL_PWD or a defaults file?

Recommendation: remove MYSQL_PWD and use a local 0600 defaults file in a private temp directory, passed only to the MySQL stage. Until then, pass the environment only to the MySQL process, never to ssh, gzip, cat, pv, or gunzip.

The remote path already uses --defaults-extra-file; local imports should match. Generate the file with O_CREAT|O_EXCL|O_WRONLY mode 0600, clean it in a finally, and never render its contents.

D5Dangerous rsync flags?

Recommendation: allowlist safe flags and require --allow-dangerous-rsync for --delete*, --remove-source-files, --rsync-path, --files-from, --log-file, --write-batch, --rsh/-e, and --copy-links. Print the effective command before execution.

An allowlist is easier to defend than a denylist because rsync adds options over time. Keep --bwlimit, --partial, --progress, --info, and --exclude (with a warning that excludes can hide files) in the safe set.

D6Whole-project pull confirmation?

Recommendation: require confirmation when the destination is a Git worktree with local changes, contains sink.yaml, or is not empty; add --force for non-interactive automation; exclude local config and secrets; offer a backup/temp-dir mode.

A pull is a write to the local trust anchor. Treat it like a deploy: show the resolved source and destination, refuse by default in a dirty tree, and never overwrite sink.yaml without an explicit opt-in.

D7Support window?

Recommendation: support the current minor plus the previous minor for security fixes for 12 months; publish a 90-day coordinated-disclosure target; backport P0/P1 only; state Python 3.15 and Ubuntu LTS as the tested baseline.

Sink executes external tools, so the support statement should include the tested OpenSSH/rsync/MySQL versions and the Docker matrix. Unsupported combinations remain “best effort” with the documented residual risks.

07User hardening playbook

These controls work with Sink 0.3.0 today and remain useful after the code fixes. The highest-leverage change is to stop treating the repository root as the deploy root.

1Narrow the root and move secrets above it

Set project.root to the directory that is actually deployed. Keep sink.yaml, pulls/, env files, keys, and dumps outside that directory. The starter config's root: . is the root cause of the largest exposure.

yaml · hardened sink.yaml
# sink.yaml — hardened starting point.
# Keep this file, pulls/, and all secrets ABOVE project.root.
project:
  name: example
  root: public                 # only deployable content
  pulls_dir: .sink/pulls       # outside root; 0700
  exclude:
    - .git
    - .sink
    - sink.yaml
    - '*.sql.gz'
    - '.env*'
    - '*.pem'
    - '*.key'
    - '.ssh'
    - '.aws'
    - '.config/gcloud'
    - '.netrc'
    - '.npmrc'
    - '.pypirc'
    - '*.kdbx'
    - '*.bak'
    - '*~'
    - '.#*'

servers:
  prod:
    root: /var/www/example/current/public
    warn: yes                  # ask before file/db overwrite
    ssh:
      - username: deploy
        server: example.com
        port: 22
        key: ~/.ssh/sink_example_ed25519
    mysql:
      - db: example
        username: sink_ro
        password: ${DATABASE_PASSWORD}
        hostname: db.internal
        port: 3306

Why this works: a whole-project transfer now mirrors only public/. The secrets are siblings of public/, not children. Even if a future exclude is forgotten, the narrow root keeps the blast radius small. Keep warn: yes on production and use a dedicated deploy key.

2Set restrictive modes and a safe umask

bash
install -d -m 700 .sink .sink/pulls
chmod 600 sink.yaml
chmod 700 .sink/pulls

# In the shell that runs Sink, before any DB pull:
umask 077

# Verify:
stat -c '%a %n' sink.yaml .sink/pulls
# 600 sink.yaml
# 700 .sink/pulls

After SEC-04, Sink creates dumps 0600 and the pulls directory 0700 regardless of umask. Until then, umask 077 is the only thing preventing a 0644 production dump on a default system.

3Run the before---real checklist

  • sink --config prints the config path; confirm it is the repository copy, not a parent or a checkout you do not trust.
  • git status --short is clean or understood; no untracked env files, dumps, or keys will be swept into a whole-project transfer.
  • Read sink.yaml: server host, username, key, narrow root, warn: yes, and no unexpected actions or difftool.
  • Run the command without --real and read the rendered rsync/ssh command. For rsync, confirm the source and destination and the absence of --delete.
  • Back up the remote database and target directory; confirm the restore procedure, not just the backup.
  • Confirm the SSH host-key fingerprint out of band; do not accept a changed key because “it is probably fine”.
  • Review --extra-flags character by character; never pass it from an untrusted wrapper or CI variable.
  • For DB work, confirm the target database and that the dump is a test restore target, not production.

4Keep secrets out of config, output, and child environments

  • Resolve passwords from a secret manager or an environment variable at invocation time, for example op run -- sink db pull prod, pass, direnv, or your CI secret store. Do not commit literal passwords to sink.yaml.
  • Until SEC-02 is fixed, use sink --config (prints only the path) instead of sink info, and never run sink info in a recorded terminal or CI log.
  • Do not put secrets in action strings. Actions are printed by sink action and executed through a shell or SSH.
  • Sink copies the parent environment into child pipelines. Do not export production secrets globally; scope them to the single invocation, and unset them afterwards.
  • Treat --show-secrets as a break-glass flag. Prefer editing the minimum field instead of dumping the whole config.

5Pin SSH identity, host keys, and agent policy

ssh_config
Host example.com
  HostName example.com
  User deploy
  IdentityFile ~/.ssh/sink_example_ed25519
  IdentitiesOnly yes
  StrictHostKeyChecking yes
  UserKnownHostsFile ~/.ssh/known_hosts_sink
  HashKnownHosts yes
  ForwardAgent no
  ForwardX11 no
  ServerAliveInterval 30
  ServerAliveCountMax 3

# Seed the host key over a trusted network, then verify the fingerprint
# against the provider console or an out-of-band channel:
# ssh-keyscan -t ed25519 example.com >> ~/.ssh/known_hosts_sink
# ssh-keygen -lf ~/.ssh/known_hosts_sink
  • Use one key per server or environment; do not share a production key with staging.
  • Generate Ed25519 keys with a passphrase and a long KDF time: ssh-keygen -t ed25519 -a 100. Load them into the agent for the session; keep IdentitiesOnly yes so Sink cannot silently fall back to another key.
  • Never forward the agent to a remote host. Sink's actions and rsync do not need it; forwarding turns a compromised remote into a key thief.
  • Set StrictHostKeyChecking yes in the config. Sink 0.3.0's rsync path does not pass this, so the SSH config is the current control; after SEC-07 it will be enforced in argv too.
  • When a host key changes, stop. Verify the fingerprint, DNS, and network path before editing known_hosts; if you already accepted a changed key, rotate the credentials used on that host.

6Harden MySQL access and treat dumps as sensitive code

  • Least privilege: use a read-only dump account with only the grants the dump needs (SELECT, plus LOCK TABLES, SHOW VIEW, EVENT, TRIGGER, and PROCESS where required). Use a separate, staging-only import account for db put. Never use root.
  • TLS: set require_secure_transport=ON on the server. On the client, require VERIFY_IDENTITY with a pinned CA, not PREFERRED. Do not use --insecure for sink check against production. Do not enable skip_secure_auth; upgrade the account/server instead.
  • Backups: encrypt dumps at rest, restrict retention, test restores regularly, and keep dumps out of Git, chat, tickets, and cloud sync folders. A dump is a full copy of production PII.
  • Consistency: --single-transaction gives a consistent snapshot for InnoDB tables, not MyISAM. Know which storage engines you have; a “successful” dump can still be internally inconsistent for non-transactional tables.
  • Verification: run gzip -t, check size and checksum, restore to a scratch database, compare row counts and a few invariants. Never restore an unverified dump over production.

7Wrap sink check so failures fail CI

Sink 0.3.0 prints [✗] lines but exits 0 on probe failure. Until SEC-06 lands, wrap it:

bash · sink-check wrapper
#!/usr/bin/env bash
set -euo pipefail

out="$(sink check "$@" 2>&1)" || {
  printf '%s\n' "$out"
  exit 1
}
printf '%s\n' "$out"

# 0.3.0 workaround: a printed failure is still exit 0.
if grep -Fq '[✗]' <<<"$out"; then
  echo "sink check reported failures" >&2
  exit 1
fi

Run this only on a trusted config (SEC-05). After the fix, prefer the native non-zero exit and --json output; keep the wrapper only if you need to support old versions.

8Make transfers boring and reversible

  • Prefer a single file or a narrow directory over whole-project transfers. Type the path explicitly; do not rely on the default root.
  • Never add --delete, --delete-excluded, --remove-source-files, --rsync-path, --files-from, or --log-file through --extra-flags. If you need deletion, do it as a separate, reviewed operation with a backup.
  • Until Sink adds --safe-links, inspect trees for symlinks before a whole-project transfer and use a manual rsync --safe-links for untrusted inputs. Do not use --copy-links or --copy-unsafe-links: they upload the target content.
  • Pull a whole project only into a clean checkout you can discard. Commit or stash first; compare the remote tree before overwriting. Assume a compromised remote can inject executable files.
  • Keep warn: yes on production for both files and databases. A prompt is not a security boundary, but it catches wrong-target mistakes.
  • After a pull, inspect git status and git diff before running tests, builds, or actions that execute newly arrived code.

9Harden the workstation and supply chain

  • Put trusted directories first on PATH (/usr/local/bin:/usr/bin:/bin), never .; verify command -v ssh rsync mysql mysqldump gzip git less points at root-owned binaries. A hijacked ssh is game over regardless of Sink's argv.
  • Use full-disk encryption, screen lock, encrypted backups, and a separate admin account. Same-UID malware can read dumps and environment variables no matter how Sink writes them.
  • Pin GitHub Actions to full commit SHAs, not tags. Verify the gitleaks archive checksum/signature before extracting; do not pipe curl directly into tar on a release runner.
  • Run uv sync --frozen, review lockfile changes, and use dependency scanning. Keep Sink, Python, OpenSSH, rsync, MySQL client, git, and less patched.
  • Use a pre-commit secret scanner and a global .gitignore for env files, dumps, keys, and .sink/. Scan history before making a repository public.

10Incident response: three concrete playbooks

If a config or dump was exposed

  1. Contain: remove the file from the web root/repo, revoke public access, and preserve logs for investigation.
  2. Rotate everything in the file: SSH keys/passwords, MySQL users, URL/HTTP-auth credentials, control-panel/hosting credentials, API tokens, and any secret in notes. Assume all of them are compromised.
  3. Audit: search SSH auth logs, MySQL general/audit logs, web access logs, and Git history for use. Check for new keys, users, cron jobs, and database accounts.
  4. Notify and document: follow your breach process; record the timeline, scope, and rotation evidence. Scan backups and CI artifacts too.

If SSH reports a host-key change

  1. Stop. Do not run ssh-keygen -R, StrictHostKeyChecking=no, or accept the new key to “make it work”.
  2. Verify the new fingerprint through the provider console, a signed message, or another trusted channel. Check DNS, your network, and whether the host was rebuilt.
  3. If the change is unexplained, treat it as a possible MITM: rotate credentials used on that host and inspect for unauthorized access.
  4. Only after verification, update the dedicated known_hosts_sink and document the change.

If a DB pull was interrupted or a dump looks partial

  1. Do not restore, rename, or promote it. Treat it as corrupt and potentially attacker-controlled.
  2. Check for a .part file, gzip -t, size, checksum, and whether LATEST-* changed. In 0.3.0 a partial final file can remain on SIGINT or startup failure.
  3. Delete the partial artifact, re-pull to a fresh filename, and verify before use. If it was already imported, treat the target database as inconsistent and restore from a known-good backup.

08Verification and test plan

Every finding gets a regression test. The fast suite is hermetic: it stubs ssh, rsync, and MySQL and can run on every commit. Real behaviour — host keys, symlinks, file modes, signals, credential cleanup — belongs in the Docker integration suite. Timing-dependent interruption cases remain manual staging checks.

Fast suite: uv run pytest -q. Docker: make integration, make integration-oldest, make integration-matrix. The review did not execute the Docker matrix or touch production; test descriptions are acceptance criteria, not claims that the fixes already exist.

## P1 — make failure/SSH honest (1–2 weeks)
8. SEC-06: Aggregate check failures; add --strict now and non-zero default next
   minor; support -qq and --json; update the test that asserts exit 0.
9. SEC-07: Apply StrictHostKeyChecking=yes, BatchMode=yes, IdentitiesOnly=yes,
   and a dedicated UserKnownHostsFile to rsync --rsh, scp, check, actions, and
   credentials. Document interactive ssh policy.
10. SEC-10: Missing configured key is a hard error in real mode; explicit agent
    fallback only; keep dry-run rendering.
11. SEC-11: Add ssl-mode/ssl-ca/ssl-cert/ssl-key; prefer VERIFY_IDENTITY; use a
    local defaults file; warn/deprecate skip_secure_auth.
12. SEC-12: Allowlist safe rsync flags; require --allow-dangerous-rsync for
    --delete*, --remove-source-files, --rsync-path, --files-from, --log-file,
    --write-batch, --rsh/-e, --copy-links.
13. SEC-13: Confirm whole-project pull in a dirty tree or when sink.yaml exists;
    add --force; exclude local config/secrets; offer backup/temp-dir mode.
14. SEC-14: Use shlex.join for --rsh; test key paths with spaces, semicolons,
    and $().
15. SEC-16: Central value-based redaction; redact action listings, URL userinfo
    and sensitive query params, check/DB stderr, and notes.

## P2 — defense in depth (2–4 weeks)
16. SEC-15: Use a remote private temp dir (mktemp -d, 0700) or O_EXCL; reject
    newline/CR/NUL in option values; use --defaults-file; clean the dir.
17. SEC-17: Validate server names and emit YAML with yaml.safe_dump/quoting.
18. SEC-18: Create LATEST before printing success; use Text/escape for Rich
    status; add git --no-ext-diff --no-textconv; neutralize LESSOPEN/PAGER/
    EDITOR or use trusted values; pin CI actions by SHA; checksum gitleaks;
    reject recursive YAML aliases; remove/deprecate skip_secure_auth.

## User controls to document
- root: public; pulls_dir outside root; warn: yes; dedicated key.
- umask 077; chmod 600 sink.yaml; chmod 700 pulls.
- StrictHostKeyChecking yes; IdentitiesOnly yes; ForwardAgent no.
- TLS VERIFY_IDENTITY; least-privilege DB users; encrypted dumps.
- No --delete/--rsync-path/--files-from; whole-project pull only to clean tree.
- Check wrapper until non-zero exit ships; rotate on any host-key change.

## Done when
- No test can upload/print/leave-readable a configured secret.
- Nested symlinks cannot escape; dumps are 0600; failures exit non-zero.
- All non-interactive SSH paths enforce strict host keys and identity.
- Config trust is explicit and the resolved path is visible.
- CI is pinned and checksummed; residual risks are documented and owned.

11Method, evidence, and limits

      
This is a source-based security assessment, not a penetration test and not a formal audit of Sink's dependencies.

      
What was reviewed

      
    
        
  • CLI command tree and option handling in src/sink/cli/, including file, db, check, info, action, ssh, and misc.
    • 
        
  • Execution layer src/sink/shell.py, transfer construction src/sink/rsync.py, database pipelines src/sink/db.py, remote credentials src/sink/credentials.py, SSH helpers src/sink/ssh.py, actions, applications, UI/redaction, and config loading.
    • 
        
  • Configuration models and loader: immutable models, environment expansion, parent discovery, SSH key resolution, unknown-key handling, YAML parsing.
    • 
        
  • docs/safety.md, the pytest suite, Docker integration tests (including adversarial, interrupt, check, and credential tests), pyproject.toml, and GitHub Actions workflows.
    • 
      

      
Evidence standard

      
Each finding cites the file and line range where the behaviour is visible. Where a claim depends on an external tool's behaviour (rsync filter precedence, --rsh parsing, MySQL option-file order, OpenSSH host-key policy), the document states the dependency rather than assuming Sink controls it. Severity is qualitative: High means a realistic path to broad credential or production-data exposure; Medium means a meaningful but narrower integrity/availability/trust issue; Low/hardening means defense in depth or operator-dependent exposure.

      

        Limitations and out-of-scope areas
        

          
    
            
  • No dynamic exploitation, fuzzing, or runtime instrumentation was performed against a live Sink installation.
    • 
            
  • The Docker integration suite was read, not executed for this review; test descriptions are plans and acceptance criteria, not current results.
    • 
            
  • No formal audit of OpenSSH, rsync, MySQL client/server, Git, less, Python, Click, PyYAML, or Rich. Their vulnerabilities are inherited.
    • 
            
  • No review of hosting-provider controls, cloud IAM, PAM/sudo/SELinux/AppArmor policy, network segmentation, or physical security.
    • 
            
  • No cryptographic design review. TLS and SSH recommendations assume standard, patched implementations and correct host-key/CA management.
    • 
            
  • No CVSS scoring; severity and priority are relative to a developer workstation that can change production. Re-score in your environment.
    • 
            
  • Line references are for the reviewed 0.3.0 tree and may move after remediation.
